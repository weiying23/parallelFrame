# Vibe Orchestrator

## 目标

把“模糊需求”变成可交付的变更：明确范围与验收口径 → 找入口 → 实现 → 验证 → 交付说明。

## 什么时候调用

- 用户提出目标但没给实现路径：例如“把这个模块做得更稳/更快”“加一个参数”“修崩溃”
- 任务涉及多个文件/多个步骤，需要统筹推进
- 需要同时兼顾：代码风格、兼容性、验证方式、说明文档

## 工作约束

- 默认按 Agent 模式推进：先做最合理假设并执行，完成后说明假设
- 修改前先理解现有约定：接口、线程模型、内存/并发边界
- 不引入新依赖：除非仓库已存在且风格一致
- 不新增注释：除非用户明确要求

## 标准流程（建议）

1. 需求压缩：列出必须做到的 3-6 条验收点（含边界条件）
2. 入口定位：搜关键路径、调用链、数据结构与配置来源
3. 风险点扫描：并发、内存生命周期、错误处理、性能退化点
4. 实现：尽量小改动、遵循现有模式；必要时补最小测试/示例
5. 验证：本地可运行验证（编译/运行/简单断言/输出核对）
6. 交付：给出改了哪些文件、如何使用、验证方式

## 产出

- 可运行的代码变更（或可复现的最小问题定位）
- 简短验收说明与使用方式
